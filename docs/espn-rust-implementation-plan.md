# ESPN Fantasy Football Rust implementation investigation and plan

Initial investigation: October 2, 2026. League foundation, weekly box scores, free-agent pages and player lookup are now available; see [README](../README.md), [foundation contract](implementation-contract.md), [weekly matchup contract](weekly-matchup-contract.md), [player search contract](player-search-contract.md) and [compatibility ledger](compatibility-ledger.md). The principal manager-facing Stage 3 features are implemented. Historical roster loading and other enrichment from earlier stages remain incomplete; no full-stage completion or live current-season/private parity is claimed. Draft/history and advanced analytics remain later milestones.

## Recommendation

Build an asynchronous **football-only** ESPN fantasy library. Establish request and data compatibility through offline fixtures before expanding the football API. A useful football manager foundation is complete after stages 1–3 below; football package parity needs stages 4–5, followed by release validation in stage 6. The other sports below are background from the requested package investigation; they are excluded from implementation and acceptance criteria.

The reference is directly under `reference/` in this checkout, not `reference/espn-api-python`. Its declared version is **0.46.0**, its license is MIT, and it contains five sports. All active HTTP operations are GET requests. “Transactions” and “offers” mean reading records, not submitting trades or bids. Lineup changes, waiver submissions, trade execution, account login, persistence, recommendations, and a manager UI are separate product work beyond this port. The username/password authentication implementation is commented out.

Treat compatibility as equivalent ESPN requests and observable data semantics. Rust method signatures, ownership, errors, and loading behavior should be idiomatic. Explicitly record corrections to reference defects instead of claiming byte-for-byte Python behavior.

## Package scope

Every sport exposes league loading, teams/owners/rosters, settings, draft picks, standings, team lookup, scoreboard, free agents, recent activity, and box scores. They share transport but differ substantially in stat interpretation and scoring shapes.

Hockey, baseball and WNBA are described as “in development” in the README. Their category/rotisserie scoring and sport-specific stat models account for much of the full package's extra scope and will not be ported. Shared low-level request methods support player cards/news across sport codes even where a league convenience method is absent. Include the shared transport, settings, `Pick`/auction data, `Offer`, and trade helpers used by football. News is a low-level shared capability, not an existing football `player_info` convenience feature.

The package consumes ESPN’s applied totals and applied stat contributions. It does not provide a complete scoring engine. A manager should use league-specific applied points, retain raw scoring settings, and keep any independent score recalculation outside initial parity work.

## Observed verification baseline

The reference includes **21 JSON fixtures totaling approximately 81.4 MiB**, all under football and hockey. Football has 2015/2018 league and draft payloads, a 2019 player card/activity payload, historical rosters, and a 2024 professional schedule. The 2018 box-score fixture alone is about 42 MiB, and its old full-fixture test is commented out. Basketball, baseball and WNBA rely principally on small synthetic payloads in unit tests.

Ran the repository’s non-integration selection in an isolated environment under `/tmp`, suppressing bytecode and pytest cache writes:

```sh
PYTHONDONTWRITEBYTECODE=1 /tmp/espn-investigation-venv/bin/python -m pytest \
  tests --ignore-glob='**/integration/**' -p no:cacheprovider \
  --basetemp=/tmp/espn-investigation-pytest \
  --junitxml=/tmp/espn-investigation-tests.xml -q
```

Result: **497 passed, 10 failed, 93 subtests passed**. Runtime: Python 3.12.14, pytest 9.1.1, requests 2.34.2, requests-mock 1.12.1, urllib3 2.7.0 and idna 3.15, satisfying the relevant dependency ranges in `pyproject.toml`.

All ten failures were proxy-denied real ESPN requests left unmocked by purported unit tests: three cases in [access-denied tests](../reference/tests/espn_requests/test_access_denied.py) and seven in [hockey league tests](../reference/tests/hockey/unit/test_league.py). Within the football implementation scope, **all 58 football unit tests passed**; relevant shared request/helper tests had **57 passes and 3 failures**, the three access-denied cases just described. These counts come from the same run, not a second run. Future offline verification must reject any unrecorded network access. No live integration suite was run; one historical football integration case is skipped in the source. Successful access to a real private league has not been verified.

The tests are evidence, not a complete specification. For example, football’s invalid-seeding test calls `standings(week=1)`, whose signature rejects that argument, and the coin-flip test compares generator identities instead of materialized team orders. Add meaningful coverage for those behaviors in the new harness without editing reference tests.

## Behavior to preserve

### Requests and errors

- Use `ffl` under the read host `https://lm-api-reads.fantasy.espn.com/apis/v3/games/` and, for low-level news reads, the separate host `https://site.api.espn.com/apis/fantasy/v3/games/`.
- Initially select `/leagueHistory/{league_id}?seasonId={year}` for years before 2018 and `/seasons/{year}/segments/0/leagues/{league_id}` otherwise. League history can return an array; normalize its first element as the Python client does. Handle empty arrays explicitly in Rust.
- On a league 401, try the alternate league endpoint once, forwarding query parameters, filters, extension and cookies. Commit the chosen endpoint only after HTTP success and successful JSON decoding; reuse it for that league/year. Failed HTTP, timeout, connection or JSON decoding must leave the original route intact. See [fallback tests](../reference/tests/espn_requests/test_endpoint_fallback.py).
- Private access uses both cookie names **`espn_s2` and `SWID`**. Distinguish missing credential pairs from credentials denied after fallback. Public access may succeed through fallback without cookies.
- A primary league 404 means invalid league; a league communication 404 yields an empty topics result. Other non-200 primary statuses produce an HTTP error; the Python fallback’s non-200 result becomes access denied. Keep these distinctions visible rather than returning an empty league.
- Preserve repeated `view` query keys and the semantic JSON structure of `x-fantasy-filter`: IDs, priorities, directions, limits, offsets, included statuses and stat-split codes. JSON whitespace and arbitrary Python set ordering are not compatibility requirements.
- Default league views are `mTeam`, `mRoster`, `mMatchup`, `mSettings`, `mStandings`; draft uses `mDraftDetail`; pro schedules use `proTeamSchedules_wl`; active pro players use `players_wl` at `/players`; cards use `kona_playercard`. Preserve football’s `mPositionalRatings` enrichment.
- Player-card filters include actual/projected season strings `00{year}` and `10{year}` and the maximum scoring period. Retain the low-level ability to supply additional filters.
- Player-pool pagination defaults to 500 records, includes `FREEAGENT`, `WAIVERS`, `ONTEAM`, extracts valid nonzero IDs from outer or inner wrappers, deduplicates in first-seen order and stops on an empty/short/non-list page. Add a termination guard for repeated full pages.

The generic season `get()` currently invokes league fallback logic and ignores its returned body, while `news_get()` performs no HTTP status validation. These are transport inconsistencies to correct, not a requirement to send a season/news request to a league route. Build URL paths before queries; the reference’s string concatenation can append a communication suffix after the history query.

### Models, periods and calculations

- Keep league ID/year, ESPN status periods, previous seasons earlier than the requested year, settings, members/owners, teams, rosters, schedule and draft data. Teams are sorted by team ID. Modern `current_week` is capped at final scoring period; pre-2018 behavior uses the response scoring period directly. Football also exposes latest NFL scoring period.
- Distinguish **scoring period** from **matchup period**. Football maps a selected box-score week through settings’ matchup periods. Preserve each operation's defaults: scoreboard defaults to `current_week`, box scores to current scoring/matchup periods, free agents to `current_week`, and transactions to the raw `scoringPeriodId`. A future football box-score week falls back to current data in the reference, while free agents accept a supplied week without the same clamp.
- Football `recent_activity`, `free_agents` and `box_scores` reject seasons before 2019. “Most recent season” in docstrings is not an enforced current-year check. League loading, draft and scoreboard support older seasons; don’t impose a blanket 2019 minimum.
- Standings use final standing when nonzero, otherwise playoff seed. Preserve team-name fallback to location/nickname, owner/member resolution, division names, schedule ordering and outcome codes. Represent missing/unknown teams and byes explicitly while retaining raw IDs. Football internally models a bye opponent as the same team, which matters for margins and analytics.
- Player inputs have roster (`playerPoolEntry.player`), pool/card (`player`) and metadata wrapper variants. Preserve identity, eligibility/slots, acquisition, team, injury, ownership, stats and available schedules with explicit paths and precedence. Do not blindly search all nested objects for the first `id`.
- Football stats exclude other seasons and split type 2, combine actual versus projected values by scoring period, and expose raw performance breakdowns separately from applied fantasy contributions. Keep aggregate period 0 totals/averages and unknown stat IDs.
- Football box players prefer actual weekly stats’ nonzero `proTeamId` over the player’s current team; absent actual stats can use the caller’s prior-week cache. Only actual evidence updates that cache. This supports historical weeks after a midseason trade and subsequent byes. See [box-player tests](../reference/tests/football/unit/test_box_player.py).
- Live scores take precedence over total points in football box scores. Missing team projections are computed from projected starters, excluding `BE` and `IR`. Preserve missing-away lineups and playoff flags.
- Preserve numeric values and rounding at the reference’s specific output fields. Python’s two-decimal rounding is not reliably reproduced by `(x * 100.0).round() / 100.0`. Keep unrounded breakdown values; test half-way and negative cases explicitly.
- Preserve the instant represented by ESPN millisecond timestamps. Football transactions use process → accepted → proposed date precedence. Python local naive datetimes become UTC-aware Rust timestamps with raw milliseconds retained. Offer timestamps truncate to seconds in Python; document that normalization.
- The reference’s `game_played` is a heuristic: 0/100 based on kickoff plus three hours, not real live progress. Keep equivalent heuristic results with an injected clock and describe their meaning. Pro-schedule helpers choose the first game within a period; expanded multi-game modeling is a later improvement.
- Football weekly standings promote division winners and apply configured recursive tiebreaker hierarchies, with half-credit ties, equal-opponent-game restrictions for multi-team H2H ties and a final random coin flip. This is library-derived standings, not a claim of authoritative ESPN playoff seeding; playoff and median-scoring coverage is incomplete.
- Power rankings use two-step dominance (`W² + W`), truncate average score/margin before weighted summation (0.8/0.15/0.05), and return descending scores. Preserve the calculation; expose a numeric score plus display formatting rather than a numeric string. Highest/lowest weekly helpers return a team and point value, despite their annotations suggesting an integer/week.

### Activity, transaction and offer history

- Default activity is 25 topics, offset 0, descending message date and message types `[178, 180, 179, 239, 181, 244]`. Preserve optional activity filters, waiver bid amounts, unknown-player ID fallback, and football trade messages yielding sent and, when resolvable, received actions. Football may fetch player cards when roster resolution fails.
- Football transaction defaults are `FREEAGENT`, `WAIVER`, `WAIVER_ERROR`. A missing `transactions` field raises an error; a present empty list returns no transactions. Preserve the distinction through typed errors/empty results.
- Trade filling is opt-in and only fetches cards when a requested `TRADE_ACCEPT` has no trade legs. Explicit player IDs override source selection. Sources are the requested week’s rosters (default, without changing loaded rosters), current rosters, or the pool at final scoring period. Deduplicate and sort IDs; fetch cards in batches of **40**.
- Prefer executed card transactions with the most trade legs per related transaction ID, falling back to transaction ID. Preserve populated rows; fill empty rows; append unseen card-only trades from the requested period. Filling existing matching rows does not apply the same period check as appending. Top-level transaction lists take precedence over nested player lists, including an empty top-level list. See [trade helper tests](../reference/tests/test_trade_fill.py) and [football transaction tests](../reference/tests/football/unit/test_transaction.py).
- Reconstruction is best effort: the selected player IDs may miss past participants, and absent evidence is not proof that a trade had no players. Expose completion/source information to a manager.
- Offers reports query one week or periods 0 through final period inclusive; map statuses, repair missing timestamps from another bid for the same player/team, group chronologically, then sort by status priority and descending amount while grouping bids for each player. Canceled offers leave fields unset; groups without timestamps are omitted. The tested `PENDING` display mapping is “Player already dropped.” Preserve raw status alongside a compatibility label so the manager can distinguish pending bids. See [offer tests](../reference/tests/test_base_offer.py).

## Rust design and deliberate changes

Start with one football library crate, public client/model/error modules, and private endpoint/request/DTO modules. A multi-sport trait hierarchy is unnecessary for the selected scope. Candidate dependencies are `reqwest` with Rust TLS, `serde`/`serde_json`, `thiserror`, and one date library (`time` or `chrono`); use Tokio for the async HTTP runtime and `tracing` for opt-in diagnostics. Pin the MSRV/dependency policy at stage 1. A blocking facade can be added only if a consuming application needs it.

| Python choice | Proposed Rust design |
| --- | --- |
| Constructors perform several network requests and permit partially loaded objects | Cheap `Client::builder()` and explicit async fetch methods returning complete `LeagueSnapshot` values; make basic and enriched loads visible so a manager can avoid the full player directory/draft/schedule cost |
| `BaseLeague` inheritance and mutable league state | Compose transport, football request builders and pure DTO-to-domain conversion; use a concrete football snapshot without an inheritance or multi-sport framework |
| Cyclic Team ↔ schedule/Matchup object references and ID-to-object mutation | Store typed `TeamId` links with lookup accessors on snapshots. Preserve an unresolved ID without requiring `Rc<RefCell<_>>` or duplicating whole teams |
| Mixed integer/string maps for positions, names and period IDs | Separate numeric newtypes and enum parsers/display labels; distinct ID→name and name→IDs indexes. An explicit compatibility name lookup can choose the first duplicate as Python does |
| `Player`, list, or `None` return selected by response cardinality | Separate single-player `Result<Option<Player>>`, multi-player `Result<Vec<Player>>`, and name lookup APIs. Normalize them back to Python cardinality only in the parity harness |
| Recursive first-key JSON search, empty-list sentinels and unchecked dictionary access | Typed Serde DTOs for known wrapper shapes, explicit fallback order, path-aware conversion errors, and `Option<T>` for absence. Retain unknown fields/raw payload access privately or through an escape hatch |
| Magic strings, unknown labels/IDs and projection `-1` sentinels | Enums with `Unknown(raw)` where ESPN can add values; raw stat IDs plus known labels; `Option` for unavailable projections. A normalization adapter can reproduce legacy sentinels |
| Local naive timestamps and ambient `datetime.now()`/random state | UTC timestamps with raw milliseconds, injected clock, injected coin-flip draws/RNG policy. Do not require Python and Rust RNGs with the same seed to emit the same stream |
| Global mutable metadata and callbacks that can fetch during parsing | Immutable metadata; copied per-league scoring rules; pure parsing followed by explicit async enrichment. Retain input/output order while batching enrichment requests |
| New request/session for each call; no timeout; raw debug response logging | Reuse one HTTP client, finite configurable timeouts, explicit retry policy and bounded concurrency. Default parity mode has no extra transient retries beyond the league fallback; redact credentials and make payload logging separately opt-in |
| Caller-mutated player-team dictionary and mutable league refresh | Named history/enrichment context for team resolution, partitioned by season, with explicit updates. Refresh builds a complete replacement snapshot atomically; historical roster reads return period-tagged data |

Do not cache away observable updates by default. Any manager cache should have explicit keys (league, season, periods, filters), expiry, and refresh controls. Keep fallback state scoped to a league/year and serialize route discovery, or start with `&mut` league handles, to avoid concurrent failed requests overwriting a successful route.

The following source defects merit explicit corrections and targeted tests, not silent emulation:

| Finding | Proposed departure |
| --- | --- |
| Football settings zip slot labels with dictionary values, so changed key order can assign counts to the wrong slots | Map each numeric `lineupSlotCounts` key directly; retain unknown slot IDs |
| Football settings mutate dictionaries in `SETTINGS_SCORING_FORMAT_MAP`; two settings instances share rule objects. `points_override or points` also discards a valid zero override | Use immutable metadata and independent rules; distinguish zero from missing |
| Football `refresh()` calls base loading without `SettingsClass=Settings`, losing football scoring-format/slot fields | Refresh always returns the same sport-specific settings type |
| `_fetch_draft()` appends picks on repeated loads/refreshes | Replace or deduplicate a fetched draft; make refresh idempotent |
| Football `types > TRANSACTION_TYPES` tests strict superset, not invalid membership | Validate every requested type before issuing HTTP; use typed transaction filters |
| Recursive player parsing resolves duplicate nested `id` keys by traversal order | Select identity from the appropriate wrapper/player path, with explicit validation |
| Football standings/ranking helpers can fail on missing ranks, empty score history or no completed games | Handle absence through `Option`/typed errors; validate week bounds and avoid panics |

Confirmed during read-only probes: settings instances share scoring-rule dictionaries, football refresh loses `scoring_format`, and an invalid-only football type set passes the existing validation expression. Keep these deviations in a compatibility ledger with input, Python observation, Rust expectation and rationale. Other listed findings follow directly from the inspected source and need dedicated characterization cases.

## Equivalence verification strategy

1. **Build the oracle outside `reference/`.** Import the untouched Python football package and its shared dependencies, intercept requests with explicit fixture routes, freeze clock/timezone, and inject predetermined random draws. Emit normalized JSON and request traces. Avoid a catch-all fake response: unexpected calls should fail. For the known access-denied test gaps, supply explicit failed fallback responses only in the external harness and identify that adapted result separately from the original baseline.
2. **Define normalization before comparing.** Replace object links by IDs, normalize timestamps to epoch milliseconds/UTC, tag absent values and non-finite numeric values, and translate Rust `Option`/enums to the legacy observable representation. Compare list order where observable, map values independent of serialization order, and set-valued filters independent of Python hash order. Preserve topic iteration order for message-board flattening. Compare exact rounded totals and use a narrowly justified tolerance for raw floating-point arithmetic, never a blanket tolerance that hides score discrepancies.
3. **Test HTTP contracts separately from parsing.** Use an in-process mock server or injectable transport to assert paths, repeated views, decoded filter JSON, cookies, request count and state transitions. Cover primary/alternate success, denied credentials, 404 communication, ordinary 404, non-200, invalid JSON, timeout/connection errors, empty history arrays, duplicate IDs, full/short/empty/repeated pagination pages and cancellation during fallback.
4. **Use fixture-derived differential tests for models and operations.** Compare football league/settings/team/draft fields, stat/projection/cache behavior, activity/transaction/report ordering and analytics. Port the synthetic edge inputs as data fixtures rather than copying Python object internals. Keep the large originals as source evidence, derive smaller relevant cases, and retain a few full-payload regression cases for nested-shape fidelity.
5. **Add adversarial cases absent from current tests.** Missing versus null versus zero, key reordering, nested ID collisions, unknown slots/stats/statuses, duplicate player names, multiple games in a period, mixed actual/projected/split/season rows, negative/half-way rounding, zero scoring overrides, no completed games, byes, invalid period/type requests and refreshed settings changes. Use property tests for ID normalization, no duplicate reconstructed trades, preserved populated trade legs, parsing without panics and isolated/idempotent snapshots.
6. **Keep live checks opt-in and separate.** Use known accessible football leagues covering historical/recent seasons, standard/PPR/custom scoring and public/private access when cookies are provided. Include multi-week playoff periods and median-scoring metadata. Compare Python and Rust against the same captured payload to avoid changing live scores causing false differences. Assert schema and consistency for live endpoints; do not freeze volatile team names/scores as permanent CI expectations. Network/auth failures report access status separately from parity failures.
7. **Gate milestones on behavior coverage.** Run `cargo fmt --check`, Clippy, unit/mock/differential tests and documentation examples for implemented modules. The parity matrix tracks request, model, error and ordering coverage per method plus intentional deviations. Coverage percentages alone do not establish equivalence. Test transport failures leave endpoint state intact, trade enrichment leaves loaded rosters intact, and failed refresh leaves the old snapshot intact.

## Remaining evidence gaps and decisions

- Fresh representative NFL payloads and successful private-league access are needed before claiming current-season/private parity; mixed-year historical fixtures cannot establish it alone.
- Football playoff/median-scoring analytics and uncommon configurations (IDP, team QB, auction/keepers) need stronger characterization before broad support claims. Preserve the reference's provided data without promising a complete custom scoring or playoff engine.
- Static ID/team-label maps can drift. Preserve raw numeric identities, unknown variants and fixture version information; label changes should be intentional and reviewed.
- Decide public API names, MSRV, supported season guarantees and whether to add a blocking facade at crate setup. Proposed default: async API, explicit loads, strongly typed IDs, UTC timestamps and semantic compatibility with documented corrections. No need to decide manager UI or deployment now.
- Keep external API write operations as a separate future investigation. Nothing in this reference establishes their routes, authentication requirements or transaction semantics.

At the end of the initial investigation, all **189 reference files** had identical SHA-256 hashes to the pre-investigation manifest, with no added or removed files; only this planning document had been added at that point. Subsequent implementation is outside `reference/` and is checked against the same manifest. Investigation logs and the content-hash manifest live under `/tmp`.
